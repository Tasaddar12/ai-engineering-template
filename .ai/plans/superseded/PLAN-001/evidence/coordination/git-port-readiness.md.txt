# Git port readiness advisory — planning only

**Recommendation:** after TASK-006 acceptance, TASK-007 can proceed within graph r4 and its existing ownership. The missing stdin field does not establish a prerequisite representation gap. A small, trusted Git-specific helper executed by the existing command runner is a feasible option; it is not a mandated design. TASK-009 checkpoint plumbing also has an argv-only route. This advisory performs no R1/R2, grants no approval, consumes no failed-review outcome, and changes none of the 39 task outcomes or graph r4.

Read `.ai/AGENTS.md`, selected plan/spec/graph, coordinator and architecture-author guidance, TASK-007/009 acceptance, frozen service-contracts/persistence, accepted TASK-002 `local_ports.py` and handoff, pending TASK-006 actual runner and handoff, and `next-git-dispatch.md`. The concrete boundary is narrow. `CommandRequest` has no stdin field, and pending `commands.py` launches with `stdin=DEVNULL`. Direct `git update-ref --stdin` consequently receives EOF; in the probe it exited zero without applying an update. Its ordinary argv form compares one target's old OID, but cannot simultaneously express another source ref's verification. Conversely, accepted `CommandDefinition.argv` preserves multiline/nonempty arguments, and the runner passes those arguments unchanged. A fixed helper can receive validated operation data as argv, construct Git's transaction input internally, and feed a child Git process without a shell or any v1 change. “Fixed argv” does not prohibit an immutable definition containing the particular request's data.

A scoped implementation route is:

1. Observe and validate actual refs and full OIDs through `CommandRunner`; distinguish the supported attached/detached/unborn/missing and failure cases using the existing DTOs. Resolve names from Git observations, handle aliases deliberately, and avoid duplicate ref entries in a transaction. A portable pathname or uncertain fact that cannot be represented must remain an explicit unsuccessful observation. Existing expectation and result fields are sufficient; `plan_id=None` remains usable for branch setup.
2. For branch publication, queue source verification and a target create/update using the requested expected target state. For integration, calculate a tree from the expected integration OID and candidate OID, create the commit object, then verify the candidate ref and compare/update the integration ref in the guarded transaction. `merge-tree --write-tree` can construct the tree without editing a worktree/index; `commit-tree -m` accepts the message in argv. A conflicted merge tree must not be published as successful integration. Checked-out target handling still needs an explicit implementation policy that preserves developer files. The low-level commit/ref operation need not implement TASK-011 worktree lifecycle or TASK-023 review-gated integration policy. [Git merge-tree documentation](https://git-scm.com/docs/git-merge-tree/2.43.0)
3. Associate the frozen operation/idempotency identities with a canonical request fingerprint and recoverable result. One option is a private Git receipt blob/ref containing the request fingerprint and prepared result OID, with receipt creation included in the guarded publication transaction. Repeated matching requests inspect that identity first; differing requests conflict. This is an internal Git receipt, not a new v1 record or canonical workflow state service. TASK-009 and later orchestration still own their prescribed intent journal and lifecycle persistence.
4. Re-observe result refs, commit parents/ancestry, and receipt after publication. A lost command result, unavailable evidence, still-running helper, or inconsistent/partial receipt observation is unresolved until reconciliation establishes the outcome; it is not permission to dispatch again. Return the existing `UNKNOWN`/`ambiguous_side_effect` with `changed=None` when change is genuinely unknown. A receipt alone does not prove the current target remains at its recorded result. Git locks and checks the requested old values together, but does not promise that concurrent readers observe a single multi-ref snapshot. Do not claim crash atomicity for receipt plus target merely from this API. [Git update-ref documentation](https://git-scm.com/docs/git-update-ref/2.43.0)

An owned helper entry in `git_ops.py` preserves the boundary if it dispatches only finite Git operations, validates the data, builds child argv itself, and uses `shell=False`. The outer command uses `LOCAL_EXECUTE` and the runner's existing explicit permission, environment, cwd, timeout and log controls. It cannot be labeled read-only merely because its executable is Python. Keep payload data out of executable source; a constant entry or `python -P -B -m git_ops <private-operation> <data>` is an example, not a new public port. The adapter must retain outer command evidence and actual Git outputs/reobservations; outer evidence observes the helper process and must not be presented as independently captured child-process `CommandEvidence`. Reading a `ContentRef` via a bound, digest-checking local evidence reader can live in the owned implementation; no `commands.py` read-method addition is necessary. Missing/truncated/redacted material required for interpretation cannot silently become success.

For portable closure, keep the entry in the already-owned flat module, use its ordinary static imports, and supply the trusted runtime directory/interpreter resolution through explicit local bindings/environment rather than absolute paths in portable argv. A controlled module search path must select the installed runtime, not arbitrary target-project code. Current installer discovery follows static imports from its existing entry points; it does not discover imports hidden inside strings. TASK-034 wiring and TASK-037 packaging already own the eventual runtime closure. A helper inside `git_ops.py` adds no separately hidden asset and gives TASK-007 no reason to edit those owners now. Installed execution itself was not tested here.

For TASK-009, `state.py` can consume the existing `CommandRunner` protocol through constructor injection and `GitRepository.inspect` for observations without adding `GitRepository.checkpoint`. With the required coordinator lock and generation/journal logic owned by TASK-009, an explicit `GIT_INDEX_FILE` binding permits `read-tree`, staging only transaction-owned paths, `write-tree`, `commit-tree -m/-F`, and single-ref `update-ref <state-ref> <checkpoint> <expected-parent>`. File arguments/pathspec files can carry larger payloads without stdin. The committed checkpoint contains events, operation identity and relocated projections; the state ref remains the acknowledgment boundary. This plumbing does not itself implement relocation validation, fsync, ownership tenure, deduplication or recovery.
