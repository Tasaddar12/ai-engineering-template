# Project context

## Why this exists

This project gives the owner and engineering agents an understandable
Markdown/YAML structure for project knowledge and approved work. The owner
wants the useful operating discipline of the supplied AI Orchestration
Template reconstruction without a large implementation framework.

## What success looks like

Records have one owner, agents have clear write scope, and plans explain
what the contract will say. Approved work can correct stale documentation
with evidence. Verification demonstrates actual behavior and exposes gaps.

## Non-goals

A package manager, agent runtime, automatic dispatcher, installed enforcement,
invented product requirements and unnecessary administrative records.

## Hard constraints

Keep the selected .ai layout, flat templates, state/PROJECT.md beside
state/STATE.md, and the user's named roles. The user controls new work through
report, templated summary and decision; exact direct instructions already
authorize their stated scope.

Use the assigned worktree only. Every commit has a descriptive message;
delivery authority and merge remain separate. Keep SPECs current in each PR
and retire exact local branches/worktrees after a proven successful merge.

## Out of bounds for agents

Do not invent or change user intent, expand the approved outcome, modify
another checkout or perform external delivery without existing authority.

## Stakeholders and context

The project owner is the decision authority. Role definitions guide agents;
they do not install processes. The supplied reconstruction is the adaptation
reference. Fine-grained draft wording remains available for user feedback.
Current work and pending actions belong in STATE.
