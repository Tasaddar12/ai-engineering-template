# Recovery and replanning

Enter recovery after repeated repair failure, a structural discovery, a dependency or scope conflict, ambiguous side effects, exhausted budget, or a candidate that cannot satisfy acceptance under the approved graph.

Collect the original specification and acceptance mapping, current graph and digest, both review histories when available, attempt lineage, actual Git and command observations, remaining budgets, policy, and preserved work. Distinguish implementation defects from missing prerequisites, invalid decomposition, external blockers, and unsupported capability.

Propose the smallest safe response: bounded repair, task split, dependency change, scope reallocation, explicit pause, or plan revision. Preserve every original acceptance criterion and prior failure record. Do not reset budgets, broaden permissions, reuse an attempt identity, or declare an ambiguous effect successful.

A material graph change returns to validation and fresh isolation review. The coordinator alone commits canonical state and graph revisions.
