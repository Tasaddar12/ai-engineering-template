# RES-002 — Git and GitHub CLI delivery identity semantics

## Question

Which official command semantics should bind safe, resumable delivery?

## Evidence and sources

Git remote get-url expands insteadOf/pushInsteadOf, defaults to the first URL, selects push URLs with --push, and returns every URL with --all. [Git documentation](https://git-scm.com/docs/git-remote).

GH_REPO supplies repository context; GH_HOST supplies a host where one was not provided or inferred. [GitHub CLI environment manual](https://cli.github.com/manual/gh_help_environment).

PR creation supports explicit --repo [HOST/]OWNER/REPO and --head; --head skips automatic forking/pushing and supports user:branch. Organization owners are currently unsupported in that head-owner syntax. The CLI dry-run flag can still push, so it cannot implement this framework's effect-free dry run. [GitHub CLI PR manual](https://cli.github.com/manual/gh_pr_create).

PR listing accepts only a branch in --head, not owner:branch. Its JSON fields include headRepository and headRepositoryOwner; its default result limit is 30. [GitHub CLI PR list manual](https://cli.github.com/manual/gh_pr_list).

## Conclusions

Resolve all effective push destinations and require an explicit, stable PR repository identity. Define cross-fork support explicitly. The framework must implement dry-run without calling external tooling. These are engineering inferences from the cited command semantics.

## Uncertainties

No live remote or credential behavior was exercised. Controlled integration tests verify the framework's adapter decisions; future CLI releases may change limitations.


## Delivery inference

Fork PR observation must verify repository and owner separately from branch and commit. A bounded listing is not exhaustive historical evidence; uncertainty must not silently authorize repeating an interrupted creation.
