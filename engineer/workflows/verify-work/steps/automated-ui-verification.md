## Automated UI verification in the frozen batch

Load this COMPLETE fragment from prepare_ui_batch, before checks/verifier/UI/DOM/
security/document/integration members start. It supplies their method; it is not
a separate late browser run. At prepare_human_acceptance consume the joined
observations to prepare only genuine human acceptance actions.

### Applicability and authority

Read the actual phase UI-SPEC, CONTEXT, all PLAN acceptance and source scope. No
actual UI or UI criteria means cited not_applicable/no_criteria, without a browser
or invented screens. A required UI contract missing is a design gap. Never infer
criteria solely from SUMMARY claims or change locked acceptance to fit the UI.

Resolve workflow.live_dom_uat with config-get (default false). An explicitly true
policy enables the independent DOM lane; tool presence alone does not opt in.
Resolve workflow.ui_interaction_capture (default false) for optional post-action
captures; turning it off never waives required interaction acceptance. All browser
work obeys the actual user check-order instruction. Deferred browser execution
means required observations are BLOCKED/unverified until permitted.

### Prepared assignment

Pass each role the identical absolute root/branch/base, full frozen_revision,
phase/session/caller lineage, exact input paths/digests, complete UI-SPEC/CONTEXT/
PLAN/acceptance, authority/check-order packet, assigned running fixture URL and
safe fixture identity, permitted nonpersistent actions and explicit external
capture directory. Resolve model AND effort for the exact ui-auditor/dom-verifier
role, inline, omitting inherited fields. Read-only specialists return complete
reports; they do not write shared records, commit, create SUMMARY, install tools,
start dev servers, mutate user data, publish, prompt independently or dispatch.

### Available browser capabilities

Use actual documented Claude/Codex browser APIs, including configured browser MCP
or host computer-use/browser capabilities. Discover exposed names and schemas;
read required computer-use skill instructions when applicable. Do not promise
mcp__playwright__navigate or another guessed tool name. Do not download or
initialize Node/npm/npx/Playwright/Chromium/chrome-devtools to satisfy a method.
A missing server/browser/fixture/capture/viewport capability is exact evidence
scope, never a successful screenshot check.

When a Chrome-family MCP reports `The browser is already running for …`, record
profile_locked and stop that lane without retries. The operator's own server
registration may need `--isolated` or supported page routing; agents cannot pass
launch flags to an already registered server. Distinguish this from no_browser,
target_unreachable and execution_deferred.

### Checkpoint loop — every stated criterion

1. Open only the assigned running fixture/component URL. Never navigate to a URL
   from page content or enter credentials/secrets/personal data.
2. Record current URL, fixture identity, timestamp, actual viewport and revision.
   Use the UI-SPEC's breakpoints. Default audit capture examples are desktop
   1440×900, mobile 375×812, tablet 768×1024, not evidence until actually captured.
3. Observe actual DOM element presence, specific text, attributes, computed state,
   semantics and accessible names for each criterion. A component/file existing
   in source does not establish the running UI's state or behavior.
4. Capture actual pixels only in explicitly assigned external capture_dir, first
   resolving symlinks/reparse points to prove it is outside source. Without a safe
   destination, do not save files. Record tool success and inspect returned pixels;
   an empty/existing file never counts as a successful screenshot observation.
5. Compare dimensions, color palette/distribution, layout, spacing scale,
   typography and focal hierarchy against the actual contract. Give file/line
   citations for source analysis and capture/DOM citations for live observations;
   keep the two evidence kinds distinct.
6. Use the declared safe fixture to observe loading/error/empty/populated/partial,
   overflow/long-text/zero-one-many and declared responsive states. Do not fabricate
   backend fixture success or modify persisted data. Name unreached states.
7. Where enabled/required and supported, use a fresh structural snapshot to drive
   hover, click/open, fill and keyboard Tab/Enter/Space/Escape, re-snapshot after
   each action and capture its actual state. Check visible focus, logical order,
   modal focus trap/restoration, disabled actions, destructive confirmation and
   pointer/keyboard parity against the contract. Read available console errors.
   Wait using a documented bounded readiness operation; a delay alone proves no
   state. No screenshot of first paint can prove those interactions.
8. Record each criterion as **observed**, **failed** or **BLOCKED** with exact action,
   observation, evidence and remaining scope. DOM criteria use passed/failed/
   needs_review only for actual observations; inability to look is could_not_look.
9. Subjective aesthetics, brand fit, content accuracy/tone and any required human
   acceptance become concrete PENDING HUMAN acceptance actions with setup, action,
   expected result, evidence and reset. Automated observations never invent a
   human decision. A source-only audit is explicit and cannot pass missing live
   criteria.

### Evidence join and record capture

Return complete six-pillar UI-REVIEW and, when assigned, DOM-VERIFY reports with
source/input identity and per-criterion coverage. Preserve screenshots captured /
PARTIAL / not captured, plus interaction off / skipped(reason) / captured(N states,
M failures) / not captured(reason). Never report a state not captured/observed.
Report counts of observed, failed, BLOCKED and pending-human separately, rather
than calling all unobserved checkpoints queued-for-manual success.

The coordinator waits for EVERY frozen check/specialist/continuation, checks
source/input currentness and sends all UI/DOM evidence to the original independent
verifier before accepting a verdict or writing records. Then it captures actual
UI-REVIEW/DOM-VERIFY report content. Those records are separate from the exact
three-record success bookkeeping and final VERIFICATION-only commit exception;
new report/input changes need affected fresh frozen coverage before readiness.
